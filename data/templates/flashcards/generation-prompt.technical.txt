1. LEARNING FIRST: HOW A TECHNICAL LEARNING CARD DIFFERS FROM CODE INSPECTION
================================================================================
Before writing a card, finish this sentence: "After reading this, the developer/engineer can ______ (trace/debug/modify/locate)." If you cannot, do not write the card.

Rules that make a card teach instead of test:
  1. ANSWER FIRST. The first line of the body is a direct, one-sentence technical answer. It identifies the exact method, class, stored procedure, control, or table involved.
  2. ARCHITECTURAL CONTEXT FIRST. Establish which tier is acting: Presentation (Windows Form / Infragistics Controls), Business/Domain (DTClass), Data Access (DAClass), or Database Engine (Stored Procedures, Tables, Triggers).
  3. EXACT IDENTIFIERS. Use real names from the graph: never write "the save method" when you can write "fGRN.Save invoking DTGRN.Save"; never write "the database table" when you can write "Inventory.GRNItemDetail".
  4. MECHANISM, NOT JUST SYNTAX. Explain HOW data flows between tiers (e.g. how UI control values map to DTProperty, which is packaged by DAMethod and passed to the Stored Procedure).
  5. NO EXAM WORDING in the body: no "Question:", "Answer:", "True or false", "Select the correct procedure".
  6. ONE TECHNICAL IDEA PER CARD. If a card tries to explain both grid cell event handling AND the entire multi-table database transaction, split it.

================================================================================
1B. TECHNICAL EXECUTION-FLOW WRITING IN CLEAR LINES (NO LABELS)
================================================================================
Teach the execution flow in order, written as clear technical sentences. NO part labels in the body: never write "Overview:", "Stack Trace:", "UI:", "Database:", or "Resolution:".

What every technical card covers (as concepts in order, never as labels):
  1. The direct answer: The lead line names the primary component, method, stored procedure, or table that fulfills the responsibility.
  2. The architectural role: Why this component exists in the 3-tier/4-tier stack and what contract it enforces.
  3. The execution chain: The sequence of calls in order:
     - FormMethod event handler on the Form
     - Delegation through the DT (Data Transfer) class
     - Invocation of DA (Data Access) methods
     - Execution of the Stored Procedure with parameters
     - Read/Write operations on target database tables
  4. Critical validations or constraints: What checks are performed (in client code vs. stored procedure), or what transaction locks/foreign keys are evaluated.

Depth by level:
  - EASY (20-70 words): Lead line, then 1-2 sentences on component definition, base class/interface, or control-to-property binding.
  - MEDIUM (50-200 words): Lead line, 2-3 sentences or 2-4 "- " steps tracing an event handler to a DT/DA call, stored procedure execution, or table write list.
  - HARD (120-380 words): Lead line (root cause or architectural trace), detailed execution chain with 3-5 steps, exact table side-effects/mutations, and concrete debugging guidance (what SP/table/flag to inspect when failures occur).

  - The UI triggers **fGRN.Save**, which runs client validation and populates the **DTGRN** entity object.
  - **fGRN.Save** invokes **DTGRN.Save**, which coordinates business validations and ref-doc details.
  - **DTGRN.Save** delegates to **DAGRN.Save** in the data access layer.
  - **DAGRN.Save** packages parameters and executes the **Inventory.IGRNSave** stored procedure.

title: Which database tables are inserted or updated by Inventory.IGRNSave when a receipt note is saved?

  The **Inventory.IGRNSave** stored procedure executes an atomic transaction writing across inventory, gate entry, and excise schemas.
  - Inserts receipt header and line records into **Inventory.GRNItemDetail** and **Inventory.GRNTaxDetail**.
  - Updates linked gate entry line statuses in **GateEntry.InvGateEntryItemDetail** and **GateEntry.InvGateEntryMain**.
  - Writes batch and tracking allocations into **Inventory.GRNItemLotAdditionalDetail** and **Inventory.GRNItemSerialDetail**.
  - Updates pending indent reserves in **Inventory.GRNIndentReserveDetail**.

CARD T-H1
level: hard
topic_key: failure-diagnosis--silent-save-failure-gate-entry
title: When saving a receipt on fGRN fails without throwing a UI exception, what methods and tables should be inspected in order?
body:
  A silent save abort on **fGRN** typically indicates a validation failure in the client layer or an unraised transaction error in the stored procedure.
  - Inspect **fGRN.ValidateForm** and **DTGRN.CustomValidation** to verify whether validation returned false before dispatching to the data access layer.
  - Check the return code parameter passed back from **Inventory.IGRNSave** to **DAGRN.Save** for non-zero error flags.
  - Query **GateEntry.InvGateEntryItemDetail** for the selected Gate Entry Number to confirm the line status is not already marked closed or used.
  - Verify whether **Inventory.GRNCustomFieldDetail** contains mandatory custom fields that failed mapping in **DTGRN.SaveRefDocDetail**.
  Set a breakpoint in **DAGRN.Save** to inspect the exact SQL parameters delivered to ADO.NET.
